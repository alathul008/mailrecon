# Python dependency integrity

MailRecon keeps the production Python dependency graph in `backend/requirements.lock`.

## Update procedure

Do not use an unconstrained upgrade as part of a lock refresh. Start from the existing direct pins in `backend/requirements.txt` and preserve the currently resolved versions unless a separately approved compatibility/security change is required.

Using Python 3.13 and a supported production platform, install the pinned lock-generation tool:

```bash
python -m pip install --disable-pip-version-check pip-tools==7.6.1
```

Refresh the lock while retaining existing locked versions and hashes where possible:

```bash
pip-compile \
  --generate-hashes \
  --no-upgrade \
  --reuse-hashes \
  --output-file backend/requirements.lock \
  backend/requirements.txt
```

Review the resulting diff for unexpected version changes. If a production platform requires a distribution that is not represented by the lock, regenerate deliberately for the repository's supported platform matrix rather than committing an incomplete platform-specific lock.

## Integrity verification

Both production Docker builds and CI install the exact lock with pip's hash enforcement:

```bash
pip install --require-hashes -r backend/requirements.lock
```

The Dockerfile uses the same lock and `--require-hashes`. CI also runs `pip-audit -r backend/requirements.lock --strict` against the resulting dependency graph.

The lock contains hashes for every locked distribution entry. Hashes are not manually copied from an individual wheel; they are generated by `pip-compile --generate-hashes` so the lock can represent the distributions needed by the supported platform matrix.

## Security rules

- Do not remove `--require-hashes` from Docker or CI.
- Do not silently upgrade dependencies during routine lock regeneration.
- Do not suppress `pip-audit` findings.
- Review any dependency version change as a separate security/compatibility decision.
- Keep the committed lock and the Docker/CI installation path synchronized.
